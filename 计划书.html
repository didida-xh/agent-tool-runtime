范围取舍（先钉死，避免中途膨胀）

  • 主线必做：任务书 ①~⑤ + 5 项指标。
  • 顺手融入（与主链路共用代码，边际成本低）：Pydantic v2 二次校验 + 错误回填、主备模型切换与熔断、高危工具人工确认、X-Idempotency-Key（仅退款场景）、mock 模型单测。

二、验收指标与口径（跑测前钉死，Day4 只执行不设计）

#指标目标口径
1端到端成功率≥ 95%判据 = 工具序列正确 + 关键参数正确 + 终答含关键事实；不判文本相似度；另人工抽检 20 条复核
2平均工具调用轮次≤ 3每任务 max(round) 求均值（按任务数平均，不按调用数）
3工具超时率≤ 1%超时次数 / 总工具调用次数；为证明指标非摆设，注入 TOOL_SLOW_RATE=0.5% 慢响应，实测应≈0.5%
4缺字段自愈率≥ 70%20 条专项任务中：首轮校验失败 → 3 轮内参数补齐并调用成功的比例
5调用链可追溯100%每任务有 Langfuse trace（LLM span + tool span 齐全），页面可复现同一链路

评测集配比：单工具 25 / 多工具 30 / 缺字段 20 / 超轮次 10 / 无解拒答 15 = 100 条。

三、技术选型（已定，不再讨论）

决策点选型理由
服务层FastAPI + Pydantic v2任务书要求；Pydantic 模型同时充当工具的二次校验层
模型DeepSeek deepseek-chat 主用，deepseek-reasoner 作对照tool_calls 格式稳定、便宜；备模型走同一兼容协议
工具调用协议手写循环，不用 LangChain Agent第 5 轮强制总结、错误回填时机、落库粒度都要自己控
可观测Langfuse Cloud + Python SDK v3v3 底层即 OpenTelemetry，不必自建 collector（自建需 ClickHouse + Redis + Worker）
存储PostgreSQL（tasks / tool_calls）+ Redis（幂等状态位）PG 存可追溯记录，Redis 只存短生命周期状态
天气工具Open-Meteo（免 key）真实业务数据以 PG 的订单/库存为准，天气只用于凑多步场景
评测并发asyncio.Semaphore(20)与任务书异步主题一致

五、逐日计划

R = 你手敲、我逐行讲；W = 我代写脚手架（建表 SQL、落库函数、HTML 渲染等重复劳动）。

Day1（11-12，约 6h）：骨架 + 工具注册表

  • 目录、venv、.env、requirements.txt；PG/Redis 启动检查（W）
  • migrations/001_init.sql：两表 + 订单/库存种子数据（W）
  • app/tools/registry.py（R）：@tool 装饰器统一承载
  • JSON Schema（required / enum / 字段 description，描述要写成"给人看的使用说明"）
  • Pydantic v2 模型二次校验（Schema 给模型看，Pydantic 给代码把关）
  • 超时（asyncio.wait_for）、权限等级（readonly 直接执行 / write 校验 confirm token）
  • 四个工具实现（R）：weather / order / inventory / refund
  • 高危确认：缺 X-Confirm-Token 返回结构化错误，不触达业务写逻辑
  • 单测 test_registry.py：四个 tool_call JSON 走完 校验 → 执行 → 结构化返回；含非法枚举、缺字段、越权三个反例

当日验收：pytest tests/test_registry.py -q 全绿；python -m app.tools.registry --list 能打印工具契约表。

Day2（11-13，约 7h）：调用循环引擎 + 落库

  • app/agent_loop.py（R）：
  • messages + tools → 解析 tool_calls → 注册表分发 → wait_for 执行 → tool 消息回填 → 继续
  • 第 5 轮注入 system 指令「停止调用工具，直接基于已有信息总结」，保证一定收敛
  • 每轮把 round 记入上下文，超时/异常也回填（模型要知道失败原因，而不是我们直接崩）
  • app/db.py（W）：tool_calls 落库（入参 jsonb、耗时、结果截断 512 字符、状态）
  • app/main.py（W）：POST /chat 串起 loop → 落 tasks → 返回 {task_id, answer, rounds}
  • 单测 test_loop.py：mock 模型返回固定 tool_call 序列，验证轮次上限、工具分发、回填顺序

当日验收：跑通「查订单 A 的收货城市明天天气，判断是否适合补发」双工具任务，select * from tool_calls where task_id=... 有 ≥2 条记录。

Day3（11-14，约 6h）：校验自愈 + 主备切换 + Langfuse

  • 错误回填文案（R，这是自愈率的关键）：
  • 结构统一为 {"error_code":"invalid_arguments","field":"date","expected":"枚举 today|tomorrow","allowed":[...],"hint":"..."}
  • 文案只描述事实与正确取值，不说"请重试"这类空话
  • 主备切换（W）：主模型连续失败 3 次 → 切备；30s 后半开探测（1 次试探，成功则恢复主用）
  • Langfuse（W）：一次请求 = 一个 trace，LLM 调用 / 工具执行各一个 span，trace_id 回写 tasks
  • scripts/selfheal_probe.py：10 条缺 required 字段任务，看首轮失败后能否 1~2 轮补齐

当日验收：自愈探针跑出趋势数字（此时样本小，只做机制验证，正式数字看 Day4）。

Day4（11-15，约 8h）★ 关键日：100 条评测 + 指标

  • evals/tasks_100.jsonl（R 判据 + 我草拟题目你改）：每条含 task_id / input / expect_tools / expect_args / expect_facts
  • evals/judge.py（R）：规则判分，按"工具序列 + 关键参数 + 终答关键事实"三段判定，输出失败原因码
  • scripts/run_eval.py（W）：Semaphore(20)、逐条落 runs/{run_id}/{task_id}.json、断点续跑（已存在即跳过）、失败清单导出重跑
  • 跑第一轮全量 → 按失败原因归类（参数错 / 工具选错 / 轮次超限 / 拒答不当 / 超时）→ 只修 Top2 问题再跑一轮
  • 产出 reports/metrics.md：5 项指标 + 失败分布 + 与目标的 gap

当日验收：5 项指标有真实数字；即使某项不达标也要有归因，不允许"没测"。

Day5（11-16，约 5h）：调用链页面 + 幂等 + 收尾

  • GET /chain?task_id=（R 聚合 SQL + W HTML）：时间瀑布，展示工具名 / 耗时条 / 状态色 / 入参摘要 / 结果截断，附 Langfuse trace 链接
  • 页面对所有字段做 HTML 转义（工具返回内容不可信），不引入前端框架
  • 幂等（有余力，R）：退款接口 X-Idempotency-Key + Redis idem:{key} 状态位，验证「重试不重复退款」
  • scripts/acceptance.py：一键输出 5 项指标对照表 + PASS/FAIL
  • README（启动命令 / 验收命令 / 指标口径）+ 踩坑记录
  • 用 Day4 脚本做最终全量跑，结果定格

当日验收：python -m scripts.acceptance 全项 PASS；任取 3 条任务，页面链路与 Langfuse trace 对得上。
